## Scope

Concurrent `ledger apply` writers that retry on `stale-revision` starve each other, and one apply takes 10 to 20 s at the current ledger size (about 1600 revisions). Profile apply, then add a waiting writer lock or a multi-record transaction so concurrent writers finish in bounded time.

## Criteria

- A profile of `ledger apply` at the current ledger size identifies where the time goes.
- Twenty concurrent writers on distinct records all finish without starving, under the container load limit.
- Revision checks, ledger history and record formats do not change.

## Decisions

- Every apply re-verified the whole journal (4.7 s at 3075 synthetic events: hashing 38%,
  validation 24%, parsing 23%, projection 11%). A derived `checkpoint.json` now caches the
  verified projection with per-file byte digests, so reads fully verify only later events.
- The global revision check stays the default. An opt-in `records` scope commits at the head when
  no later event touches a named record, since a waiting lock cannot refresh a caller's revision.

## Outcome

Apply on the synthetic ledger fell from 4.7 s to 0.26 s with event files and history unchanged.
Twenty concurrent records-scoped writers on distinct records each commit once.
