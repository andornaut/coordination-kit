## Scope

`validateProjectConfig` rejects unknown keys under delivery-kit's `git`, `gate`, `resources`, `ci` and `deploy` sections, although this kit reads only `reports`. A new delivery-kit setting then breaks inbox snapshots, scheduled reviews and event flushes until this kit is released.

## Criteria

- This kit validates `reports` and the top-level shape, and passes the other sections through unread.
- delivery-kit's own validation of its sections is unchanged.
- `docs/configuration.md` states which sections each kit validates.

## Decisions

- delivery-kit 5.0.1 has no validation of its own sections: its runner commands and `check-config`
  load the file through this kit's `loadProjectConfig`. That function and `validateProjectConfig`
  therefore keep the full rules by default, so delivery-kit's validation is unchanged without a
  delivery-kit release.
- This kit's readers use a separate, explicit `loadReportsConfig`/`validateReportsConfig` whose
  `ReportsConfig` type exposes only `schema` and `reports`, so the compiler stops a coordination
  command from reading an unvalidated delivery section.
- The top-level shape stays strict (exactly the seven sections and `schema` 1, no secret-like key):
  a new top-level section is a schema change for both kits.

## Outcome

Inbox snapshots and acknowledgements, scheduled reviews, route resolution, event flushes,
`claude channel` and review readiness validate only the top-level shape and `reports`, and accept
unknown keys in the delivery sections. A malformed `reports` is still refused. The exported API only
gains `loadReportsConfig`, `validateReportsConfig` and `ReportsConfig`; `addressedRoles` accepts any
value with `reports`. `docs/configuration.md` states which sections each kit validates.
