## Scope

Protocol commands map every error code outside an allowlist to `protocol-operation-failed`
(`src/commands/protocol.ts`), so an input-shape mistake, such as `writer` in place of `context`
for a work command, gives no hint of the cause. Report the cause without exposing input values.

## Criteria

- A missing or invalid input field reports a normalized code and the field path, for example
  `invalid-input` with `/context`.
- An unexpected error keeps a generic code and names the operation stage that failed.
- No error output contains input values, bodies or secrets.
- Existing error codes and exit codes do not change.

## Decisions

- Each command checks its input file against the store rules before the store call. Only an
  envelope failure (a missing or non-object `context` or `writer`, or an invalid or unregistered
  role) stops it there, with `invalid-input`; it previously failed without a code.
- A store refusal keeps its code and exit code, and gains `path` and `rule` when the checked input
  explains it, so inputs that already had a code keep it.
- A failure the store raises without a code becomes `invalid-input` at the first invalid field;
  otherwise it stays `protocol-operation-failed` with a `stage`.
- `invalid-envelope`, `invalid-worker-target`, `stale-root` and `protocol-not-configured` are
  surfaced. Enrollment evidence failures keep `enrollment-unavailable`, because that code already
  reported them.
- A boundary `approved-work-required` for `--work-id` points into the work publication with
  `unapproved`, `unknown`, `required-evidence` or `guarded`, from a new
  `WorkStore.authorizationGap`.

## Outcome

Protocol command errors report a JSON pointer and rule name, or a stage for unexpected failures,
and never input values. `docs/work-protocol.md` documents each command's input shape, the
phase-to-evidence mapping and the error fields.
