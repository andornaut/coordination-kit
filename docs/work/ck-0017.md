## Scope

Implement the coordination-kit part of Phase 2 in the [simplification design](../design/simplification.md#phase-2-one-store-and-one-message-path): the SQLite store, `msg send|done|retain|status|history`, `inbox`, wake adapters, stored briefs and runner events, `events ingest`, and `store import|export` with the cutover and rollback procedure.

## Criteria

- Every send is durable before any native action, and recipients pull.
- A message closes with one write.
- Import keeps every original ID, body hash, link and evidence, with uncertain deliveries flagged `unconfirmed`.
- The Phase 2 exit criteria in the design hold.

## Decisions

- The store is `<stateRoot>/coordination.db`, or `var/coordination.db` without an active work
  protocol, beside the wake files. Each command is one `BEGIN IMMEDIATE` transaction; no native
  call runs inside one.
- Projections are tables with one applier per event kind. A kind without an applier is still
  chained, so the later Phase 2 work adds its projections and picks up existing events on rebuild.
- The fence refuses `caller-ambiguous` when both harness variables bind a role, as in a session
  started from another harness's shell; `--native-id` settles it. Reads and the import dry run
  take no caller.
- `msg send` output carries only the wake status, never harness detail, so both adapters print the
  same JSON. A repeated send of the same original retries only the wake.
- A guard refusal leaves no outstanding wake and the next send checks again, since nothing native
  happened. Accepted, failed and ambiguous wakes stay outstanding until the recipient's pull or
  `rearmWake` from the review.
- The Codex wake uses the existing guarded queue path unchanged, so it also requires the
  recipient-bound decision marker before the native question check.
- Import maps `held` to `retained` (it carries a retention) and `parent-required` to `delivered`
  (the recipient role's conversation accepted it). The state-root copy of an ID wins over the
  pre-activation copy. Legacy close times are unknown, so `closedAt` is null.
- Closing or retaining a message still `sent` also sets its delivery time, since the recipient
  acted on it. Bodies over 1 MiB are refused.
- `inbox` alone is the store read; `inbox snapshot` and `inbox ack` keep their meaning. Help shows
  positional IDs as upper-case tokens.
- On a copy of the live legacy stores the dry run mapped 2680 records (1889 handled, 760
  superseded, 30 retained, 1 retained unconfirmed) and found the 2638 pre-activation records to be
  duplicates, 144 of them older snapshots. The synthetic 30,000-message store measured p95 2.9 ms
  for send, 0.7 ms for inbox and 0.6 ms for done in process.

- Runner events arrive through `events ingest` per the agreed contract with delivery-kit 6.1:
  the runner is the only writer of `events.jsonl`, ingest the only reader. The cursor carries the
  live file's first line id, inode and dev; a file without a first id matches only by inode and
  dev. The live file is opened before rotations are listed, so a rotation in between is read once.
  An unterminated tail of a rotated file, which no writer can finish, is quarantined.
- Every non-quiet runner event is a stored message from `delivery-kit`; COMPLETE is unique per
  (game, sha) and fires on gate ok or `gate_skipped`, push ok, CI ok and deploy ok or skipped
  (`deploy_disabled`). Progress types never count. An imported legacy `complete` line is that
  commit's COMPLETE, and an imported 1.x COMPLETE message suppresses a new one. Each work ID is
  recorded once per game. Ingest reads only `reports` from the game configuration.
- The store-mode switch is the store cutover fence in `var/work-protocol-fence.json` plus an
  existing `coordination.db`, not a `config.json` field, so a 1.3 CLI never meets an unknown
  field and restoring the previous fence is the whole switch-back. The fence keeps the previous
  configuration and a generation one higher; the configuration and `workspace.json` keep theirs,
  so role epochs and enrollment survive. A 1.3 reader sees a fence unequal to the configuration
  and fails closed; 2.0 refuses only legacy message writes and keeps the work protocol, ledger and
  legacy reads working.
- In store mode the review brief is one stored message per (game, slot) with a derived ID, capped
  at 60 lines and 4096 bytes, with `review show` for detail. Stalled means open at two distinct
  briefs of the game. Store records come first and the native checks stay where available: the
  brief runs the legacy collectors for Codex question state and child health before its
  transaction and reports pending questions, failed workers and unreadable state as exceptions;
  only an unavailable check is unknown.
- Review health from this kit is stored as messages in store mode through one emit port. Its wake
  waits for the next send or review, since the port is synchronous.
- `harness doctor` compares `var/claude-channel.mcp.json` with the stable channel command and
  reads a status file the channel writes at start; neither changes the exit status.

## Outcome

Released in 2.0.0: the store with `msg` and `inbox`, wakes, the legacy import and export,
`events ingest` with COMPLETE, stored review briefs and `review show`, coordination events in the
store, the doctor channel checks and `store cutover` with its runbook. `events flush`,
`review deliver` in legacy mode and the event outbox are unchanged for 6.0 runners. The live
cutover and the Phase 2 exit criteria remain with game-coordinator.
