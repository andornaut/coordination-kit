## Scope

A read-only `coordination-kit status` over every registered repository joins work-file front
matter, live protocol state, linked ledger requests and delivery evidence (the first commit on
`main` citing the work ID, whether `origin/main` contains it, and the first runner COMPLETE event
covering it) into one derived status per item. The work-file convention gains `proposed` and
`declined`, so every user request has a work file.

## Criteria

- Each item reports one of requested, proposed, approved, in-progress, landed, deployed, done,
  declined, cancelled or superseded (with the replacement ID); blocked items report the blocker
  and owner when known.
- Filters: `--scope`, `--since`, repeatable `--state` and `--audit` for user-originated items
  with their evidence; JSON output by default and a `--format markdown` digest per repository.
- `work check` accepts `proposed` and `declined`.
- The command writes nothing and performs no network access.

## Decisions

- Landing is the oldest commit on `main` that cites the ID in its message, changes the work file
  (following renames from a pending name) or has the title as its subject, excluding commits that
  touch only `docs/work/` and `docs/design/` and the commit that adds the work file; those are
  proposal, approval and numbering commits, not delivery.
- Repositories are read with two `git log` passes each: history with first-parent changes,
  release tags and parents, and a first-parent unbounded-context diff of `docs/work/` that yields
  each file's current text on `main`. Ancestry, `origin/main` containment and the first covering
  COMPLETE event or release tag are computed in memory, so Git calls do not grow with items.
- Front matter `done` without deployment evidence reports `landed`, so `done` always means
  delivered; a repository with no deployment channel needs only `done`.
- A work file supersedes another only when it is not `proposed`, `declined` or `cancelled`.
- Ledger requests reach a work item only through a publication's request IDs (or the same ID);
  unlinked requests and approvals are `requested` under their owner's repository, with terminal
  ledger states mapped to `superseded`, `cancelled` and `done`.

## Outcome

`coordination-kit status` reports every registered repository's items with one derived status,
blockers, pending questions and delivery evidence, as JSON or a Markdown digest, without writes or
network access. `work check` accepts `proposed` and `declined`, and the convention gives every user
request a work file.
